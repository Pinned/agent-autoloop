# 业务任务与执行轮次分离（已确认设计）

## 问题与目标

桌面当前按执行轮次列卡，预览取最新事件。一轮结束不代表事情完成；回答和更正也不是新需求。需要固定原始需求、一件业务任务一张卡，并保留真实的处理时间线。

调度事项 lane 用于串行、并发、会话和卡片范围，不能直接用作业务任务身份：规则未写 parallel 时多个不同对象共用一个 lane。不能按规则名、标题或会话猜测合并。

## 推荐边界

在事实协议中引入独立业务任务身份，不改变 lane 的调度职责。身份由中台记录并传承，来源文字不能改变 Agent、目录、权限或调度规则。新任务保存明确的原始事件引用；续办通过已记录的提问、复查或更正父关系继承身份，不能把续办文字覆盖为原始需求。

推荐新身份路径每轮只处理一个业务任务；同一任务的多个事件仍可合并，同 lane 的不同任务只串行排队、不合并。原因是现有回执没有逐任务结果、提问和复查归属，多任务共用一轮需要额外设计整套逐任务回执，范围更大且容易串用决定。旧轮次可能已经混合多个任务，按旧执行记录独立展示，不强行拆分或伪造归属。

## 具体协议草案

- 中台创建内部 `task_id`，保存 `rule`、`source`、`origin_event_id`；task 与 run 一对多，原始事件引用不可被回答覆盖。
- 外部事件可选提供 `taskKey`，仅是资料关联键，按来源与规则隔离；相同显式键才关联同一任务，不能附到其他来源或规则的任务。不提供时，每个新事件创建独立任务；重发同来源同事件 id 仍沿用原去重结果。一个事件匹配多个规则时各自创建任务。
- 回答从 card、业务复查从 timer、更正从原 run 继承 `task_id`；周期规则的新触发默认新任务。Job 增加任务身份与原始需求引用，保留旧字段兼容。
- run、card、timer、hold 记录任务归属；队列合并和失败搬运只允许同任务。新任务的卡片 key、复查 key 和历史决定按任务隔离；新路径 resolve 仅允许本任务，旧身份缺失路径保持明确标记的旧行为，不能静默扩大新任务的操作范围。
- Result 增加可选 `taskStatus: "active" | "completed"` 任务收尾声明，完成投影保存 `completed_run_id`，最终结果取明确收尾轮次，重开清除收尾引用；`done` 仍只表示轮次结束；缺少明确收尾或仍有开放提问/待复查时不标最终完成。交付反馈是评价事实，不自动当成验收通过。验收时间线只显示明确反馈或已记录验收事实，不补造新的验证结论。
- 桌面业务列表的一张卡只是 task 的视图，不改变通道现有 ask/notice 的卡片身份与回答协议；多个决策作为该业务任务内的子项展示，不要求通道改为单张主卡。新增业务任务只读查询，旧 `/v1/ui/task-runs` 执行历史继续保留。

这会改变新任务的事件合并语义及新任务内部提问/复查范围，不是仅做 UI 调整。本人于 2026-11-14 通过决策回答选择推荐方案，已授权实施。

业务状态独立于执行 outcome：done 仅说明本轮结束；开放提问表示等待决定；回答已入队但未领取表示等待继续执行；领取后表示执行中。存在未完成复查或明确未验收项时不能宣称最终完成。验收与完成只能展示已记录的明确事实，不分析自然语言摘要猜测验收通过。

## 兼容与查询

不改写旧事实，不迁移业务数据；派生关联在正常投影重建流程中从旧日志的明确父关系重建。历史不能可靠关联时单独展示并解释，不因 lane 相同就合并。

原始需求区分：旧中台未提供字段、确实未填写详情、历史原始资料缺失。标题缺失时提供明确占位，不以规则、提问或完成摘要冒充。

新增业务任务列表与详情查询，旧执行轮次查询保留兼容。服务端查询、分页、预算与权限保持有界；列表按业务任务去重，并按固定创建时间降序、编号降序和身份种类稳定分页，避免旧执行记录的独立大编号压住新任务；详情按事实时间线独立分页，轮次编号与诊断资料可展开。
